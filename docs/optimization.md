# 購入プラン最適化の仕様 v1

この文書と `app/domain/optimization.ts` が、UI・商品カタログ・Rust/WASM 間の契約です。`tests/fixtures/optimization.ts` に架空価格の受け入れ例を定義しています。Rust/WASM の入口で実行時入力検証を行い、Web Worker 内で計算します。

## 対象範囲

同一店舗・同一時点で購入可能な、内容と税込価格が確定した単品・セットを扱います。単品も `Offer` として表現します。希望数以上を満たす組み合わせを求め、余りは許容して結果に明示します。希望していない商品がセットに含まれる場合も余りです。

販売数・在庫には上限がないと仮定します。選べるセットは前処理で合法な選択肢の組み合わせを固定内訳の販売単位へ展開し、追加料金を整数で加算します。販売期間が確認済みの商品は、前処理で購入日（日本時間）に合わせて除外します。クーポン、同時購入限定の追加割引、配送料、店舗比較、アレルギーや「余りを禁止する」条件は対象外です。ソルバーに渡したカタログは計算中に変更せず、計算結果はその入力スナップショットに対してのみ有効です。

## 数理モデル

商品 i、販売単位 j について、次を定義します。

- dᵢ: 希望個数。入力から省略した商品は 0。
- aᵢⱼ: 販売単位 j に含まれる商品 i の個数。
- cⱼ: 販売単位 j の税込価格（整数の円）。
- xⱼ: 販売単位 j の購入数（0 以上の整数）。
- sᵢ = Σⱼ aᵢⱼxⱼ − dᵢ: 商品 i の余り。

制約は、すべての商品に対して **Σⱼ aᵢⱼxⱼ ≥ dᵢ** です。

次の目的を辞書式に最小化します。上位目的を最適値に固定してから次の目的を解きます。重み付き和で近似してはいけません。

1. 合計金額 P = Σⱼ cⱼxⱼ
2. 全商品を合計した余り S = Σᵢ sᵢ
3. 購入する販売単位の総数 U = Σⱼ xⱼ（異なる種類の数ではない）

P・S・U がすべて同じ購入プランが複数ある場合、いずれも正解です。特定の offer ID の優先順位は要求しません。結果の行順は ID 昇順に統一します。

希望リストが空なら、空の購入プラン（P=S=U=0）が最適です。商品自体がカタログに存在しない希望は不正入力、商品は存在するが販売単位で供給できない希望は購入不可です。

### 有限の探索範囲と整数演算

D = Σᵢ dᵢ とすると、最適解の少なくとも一つは U ≤ D を満たします。実行可能な任意の購入プランから、取り除いても希望数を満たす販売単位を順次除きます。残った各販売単位は、少なくとも一つの希望商品の不足を防ぐために必要です。同じ商品を理由に残る販売単位は dᵢ 個以下なので、残る総数は D 以下になります。価格は非負で、除去により金額・余り・購入数が増えることはありません。無料の商品を含む場合にもこの境界が使えます。

v1 の入力上限では D ≤ 10,000、最適解の金額は 10,000,000,000 円以下、各商品の供給数は 1,000,000 以下、全商品の供給数は 100,000,000 以下です。32 bit 整数では金額が収まらないため、Rust 側の金額・集計・目的値には 64 bit 整数を使います。JSON/TypeScript 側では安全な整数の範囲に収まります。

## 入力契約

`schemaVersion: 1` とカタログ・希望リストを一緒に渡します。商品・販売単位 ID は静的カタログ内で安定した正の安全な整数です。金額・数量・ID に NaN、Infinity、小数、数値文字列は使えません。

| 項目 | 条件 |
| --- | --- |
| products | 0～100 件、商品 ID は一意、name は空白だけでない文字列 |
| offers | 0～5,000 件、販売単位 ID は一意、name は空白だけでない文字列 |
| priceYen | 0～1,000,000 の整数。無料を許容、負数は拒否 |
| offer.items | 1 件以上、同じ販売単位内の商品 ID は一意、存在する商品を参照 |
| offer.items[].quantity | 1～100 の整数 |
| demand | 商品 ID は一意、存在する商品を参照、各 quantity は 1～100 の整数 |

上限値は `OPTIMIZATION_LIMITS` にも定義します。ゼロの希望数は UI が行を省略します。重複行の自動合算、文字列からの数値変換、丸めなどの暗黙の補正はしません。商品 ID と販売単位 ID は別の名前空間なので、両者で同じ数値は使用できます。

v1 の実行時検証は、未対応 schemaVersion を `unsupported_schema`、必須フィールド不足・型不一致・空の名前を `invalid_structure`、整数条件違反や負数・ゼロ数量を `invalid_number`、有効な整数の上限超過を `limit_exceeded`、商品・販売単位 ID の重複を `duplicate_id`、items/demand 内の商品重複を `duplicate_product`、不明な参照を `unknown_product`、空の内訳を `empty_offer` として返します。複数の違反がある入力では、どの違反を最初に返すかは保証しません。未知の追加フィールドは無視し、schemaVersion による互換性管理を行います。TypeScript の型だけでは外部 JSON は検証できません。Rust の入口で検証することを ソルバー実装の完了条件とします。

## 出力契約

| status | 意味 | 画面での扱い |
| --- | --- | --- |
| optimal | P・S・U すべての最適性を確認できた | このカタログ内の「最安値」と表示できる |
| infeasible | 希望数を満たすプランが存在しないと確認できた | 購入不可と表示 |
| time_limit | 計算時間を超えた。実行可能な暫定解があれば incumbent、なければ null | 最安値・購入不可とは断定しない |
| invalid_input | 入力契約違反。code と人向け message を返す | 入力またはデータの問題を表示 |
| error | ソルバー内部・WASM などの予期しない失敗 | 再試行可能なエラーを表示 |

`PurchasePlan` の purchases は購入数が正の販売単位だけを、重複なく ID 昇順で返します。surplus は希望数を引いた正の余りだけを、重複なく商品 ID 昇順で返します。totalPriceYen、totalSurplusQuantity、totalOfferQuantity は必ずその内訳から再計算できる値です。暫定解にも希望数を満たす制約と同じ集計ルールを適用します。

金額の最小化だけ証明できていても、余り・販売単位数の最適化が時間切れなら `time_limit` です。Rustは200,000探索ノード、Workerは起動・ダウンロードを含め5秒を上限とします。どちらの上限も `time_limit` とし、探索完了前に最適性は主張しません。キャンセル・入力変更でWorkerを終了します。結果を画面へ適用する側は、計算開始後の入力変更を検知し古い結果を表示しない必要があります。

## 例と受け入れ条件

以下はすべて検証専用の架空価格です。KFC の実価格ではありません。

- チキン単品 300 円、ポテト単品 200 円。
- 固定セット（チキン2個・ポテト1個）650 円。
- 希望がチキン3個・ポテト1個なら、セット1個＋チキン単品1個＝950 円、余り0個が最適です。
- セットを500円とする別例で、チキン2個だけ希望するなら、セット1個＝500円・ポテト1個余りが、単品2個＝600円より優先されます。

実行可能な例は `tests/fixtures/optimization.ts` を正とします。`npm run contract:test` は、小さな入力に対するテスト専用の全探索で期待結果の実行可能性と P・S・U の最適性を検証します。このテスト自体はアプリ用ソルバーを実行しません。`npm run solver:test` が生成済みWASMを呼び、これらの例と小さな問題80件を独立した全探索に照合します。

ケースには単品、セット、併用、余り、同額時の二段階の比較、購入不可、空の希望、無料商品を含めます。不正入力・探索上限はWASMテスト、Workerの時間切れ・キャンセルはブラウザテストで検証します。カタログは `app/data/catalog.ts` で管理します。DB・バックエンドは使用しません。


## 実装方式とWASM ABI v2

### セットの前処理

`app/data/kfc-bundles.json` が固定内訳、選択グループ、選択数、1個ごとの追加料金、出典と確認日を持ちます。同じサイドの重複選択は組み合わせとして列挙し、順序だけが異なる候補は作りません。3種類のソースは各1個ずつです。ナゲット5ピース・ディップチキン4ピースはそれぞれ1商品として扱います。希望していないソースやキッズグッズも内訳と余りに含めます。展開後は871販売単位・35商品です。単品IDは公式IDの数値部分、セットの構成IDは公式IDの数値部分×10,000＋構成の連番です。

希望商品を一つも供給しない候補は除外できます。候補Aが候補B以上の希望数を供給でき、Aの方が安いならBは除外できます。同額なら、Aの内容の総数がB以下である場合だけ除外します。実行可能プランの余り総数は「購入した内容の総数−希望数の総数」なので、これで金額・余り・販売単位数の目的を維持します。希望数を超える供給量は比較時に希望数へ切り詰めます。削除するのは計算候補だけで、残した候補の実際の内訳は変更しません。小さな問題の独立した全探索と照合して検証します。

### ソルバー

`solver/src/lib.rs` の探索は販売単位ごとの整数購入数を列挙し、未充足商品の供給可否・商品ごとの最低単価の下界・現在の目的値で枝を刈ります。購入数は、その時点の不足をすべて満たすために役立つ数を上限にします。それを超える数は非負の価格・余り・購入数を改善しないため、最適解を失いません。各候補は (金額, 余り, 販売単位数) の整数タプルで比較します。探索を完了すれば三つすべての最適性を保証し、上限到達時は未確定の暫定解だけを返します。問題規模に対して最悪指数時間です。

WASMへの転送はJSON UTF-8です。呼び出し側が `allocate(length)` で領域を確保し、入力を書いて `solve_json(pointer, length, budget)` を同期実行します。`result_ptr()` / `result_len()` で出力をコピーしてから、`release(pointer, length)` で入力領域を解放します。出力は次のsolveまでRustが保持します。ポインタはこの手順で得た領域だけを使います。メモリ成長に備えてsolve後はメモリバッファを取り直します。これらは `app/lib/wasm-api.ts` に閉じ込め、画面は型付きのWorkerクライアントだけを使います。
